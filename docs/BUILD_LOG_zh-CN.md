# pi-deepread 开发手记：从一条推文到单文件扩展

[English](BUILD_LOG.md) | 简体中文

> 这不是一份教程式的文档，而是一篇踩坑与取舍的叙事记录。所有代码由 AI 辅助完成，需求、设计、踩坑定位与实测验证来自真实开发过程。文内所有数据均为本机实测。

## 起因：一次搜索就能拿到全文，为什么要发两次请求？

起因是看到忒修斯的船板那篇 [DeepSeek Search/Fetch 实测](https://x.com/Arcadia_Bao/article/2111711040757006401)。里面有一句话让我立刻坐直了：

> 默认必须开 `need_content: true`，不加价，仍 0.005 元/次。

意思是一次搜索请求，返回的不只是标题和摘要，还包含了每条结果提取好的**整页正文**——实测单条有 3.7k 到 12.6k 字，arXiv 页面甚至能拿到近 3 万字。

我当时日常用的是 `pi-web-access`，它的逻辑是经典的"先搜再抓"：搜索返回一堆 800 字以内的 snippet，模型觉得信息不够，再发起一次 `fetch_content`。两次网络往返，延迟直接翻倍。如果一次搜索就能把正文带回来，绝大多数"搜完再抓"的动作根本不需要发生。

既然官方扩展没开这个开关，那就自己动手做一个。

## 刚跑起来就撞墙：TUN 代理与 Fake-IP 的误伤

写好第一版原型，调用抓取，立刻弹出一行红色报错：

```text
Error: Blocked internal address for x.com: 198.18.0.14.
This address is in 198.18.0.0/15, commonly used by TUN/fake-IP proxies.
```

我第一反应是代码里的 SSRF 防护逻辑写错了，`x.com` 怎么可能算内网地址？

排查了一下本地网络才反应过来：我机器上开着 Clash/Surge 这一类 TUN 模式的代理。为了做透明分流，所有域名的 DNS 解析都会被拦截并分配一个 `198.18.x.x` 的伪 IP（fake-IP），真实请求由代理客户端在底层按域名转发。而扩展为了防止恶意网页诱导 LLM 访问云厂商元数据（169.254.169.254）或内网服务，把所有保留地址段全部拦截了，`198.18.0.0/15` 正好撞在枪口上。

改法很简单，在配置文件里加上豁免：

```json
{
  "ssrf": {
    "allowRanges": ["198.18.0.0/15"]
  }
}
```

这里的设计取舍需要说明白：加这行配置等于告诉工具"信任这个网段由代理接管"。在 TUN 代理环境下这确实很安全，但如果你脱离了代理环境，这个豁免就会变成真正的安全开口。因此它必须是手动开启（opt-in），绝对不能作为默认设置。

## 抓包探底：写代码前必须用 curl 摸清的潜规则

配置修好之后，我顺手去抓原推文的正文，结果 `x.com` 返回 `HTTP 403`。换成 `r.jina.ai` 代理，又直接撞上 Jina 的风控名单：

```json
{"code":403,"name":"AbuseAlleviationError","message":"Anonymous access to domain x.com blocked until Sun Oct 18 2026..."}
```

最后只能找朋友把网页正文复制出来贴给我看。

这个插曲给我提了个醒：抓取工具的失败往往分三层——网络层（超时与 429）、站点层（403 与登录墙）、平台层（Jina 这类公共代理自身的名额或黑名单）。第三类最容易让人怀疑自己的配置，其实跟本地代码一点关系都没有。

为了不再踩暗坑，我决定在写扩展代码之前，先用 curl 逐一测试 DeepSeek 接口的真实行为。事实证明，这一步非常明智：

### 1. `need_content` 默认是关闭的

不开 `need_content` 时直接打接口：

```text
content_len = 0
summary_len = 431
```

返回的只有一段 431 字的摘要。显式加上 `need_content: true` 之后：

```text
content_len = 3739 / 12614
authority = 3, rerank_score ≈ 2.19
```

单条正文立刻变成了数千到上万字。如果我没做这一步验证就直接写代码，搜索依然能跑通、有标题有链接，看起来一切正常，但我拿到的永远只有短摘要，我可能还会误以为是 DeepSeek 接口抽不出正文。

顺带一提，DeepSeek 原生返回的 `authority`（0–4，≥3 极权威）和 `rerank_score`（0–3，≥1.5 优质）非常实用，直接拿来用就好，不需要自己在本地算权重。

### 2. 128 字符硬限制与算子陷阱

我原本把 `domainFilter` 和 `recencyFilter` 编译成了 `site:` 和 `after:` 算子，直接拼进 `query`，觉得省去了一层参数很省心。结果一条稍微长一点的搜索直接被接口拒掉：

```text
HTTP 400 {"error":{"message":"'query' must be at most 128 characters (request_id: ...)"}}
```

原来 DeepSeek 算的是拼接完成后的最终字符长度，算子字符也计入这 128 个字符的硬顶。

解决办法：拼装完先计算长度。如果超标且配置了 Exa key，就直接整条转给 Exa（Exa 没有这个长度限制）；如果没有 Exa key，就直接报错，并在错误提示里把拼好的完整 query 原样打印出来。

把上下文写进错误信息里，未来排查问题时一眼就能看到是哪里超了字数。

### 3. 并发 10 会被限流，并发 3 刚刚好

实测数据显示：10 线程并发请求时，大约 30% 的请求会在 0.6 秒内收到 `HTTP 429`。

虽然 429 不计费，多试几次在经济上没损失，但退避重试带来的延迟会让体验极差。

第一版我写了纯串行 + 900ms 固定间隔，绝对安全，但抓取 4 个 URL 整整花了近 6 秒。

最终的方案是**3 个并发槽位 + 起始间隔 gap/3（300ms）**：
- 同时在飞的请求上限为 3 个（不触发限流）；
- 新请求的发起时刻按 300ms 错开。

同样抓取 4 个 URL，耗时从 5.71 秒缩短到 **2.85 秒**，一条 429 都没遇到。

## 岔路：放弃打补丁，自己写一个单文件扩展

中途我去看过 `pi-web-access` 的实现，发现它在打包代码里直接把内容截断了：

```javascript
snippet: (text4(entry.summary) || text4(entry.snippet)).slice(0, MAX_SNIPPET_CHARS4)
// MAX_SNIPPET_CHARS4 = 800
```

而且请求体里完全没发 `need_content`（`grep -c need_content dist/index.js` 结果为 0）。上游相关 issue 挂在那里，一直没人处理。

我一度想过图省事直接给它的 bundle 打补丁，把 800 替换成 8000。改完运行 `node --check` 也能通过。但冷静下来想了想，还是放弃了这个念头：

1. 扩展只要一升级，补丁直接被冲掉；
2. 在 1MB 混淆后的单文件 bundle 里塞私货，后续出了问题根本无从排错；
3. 最核心的是，我真正想要的不仅是把 800 改大，而是正文落盘、支持分页、能通过 `findText` 按段落检索。

于是我决定重新写一个：1300 行 TypeScript，单文件，零运行时依赖。事后证明这是整个项目里最正确的决定。

## 本地文档解析：anymd 带来的惊喜与连环暗礁

网页内容可以通过 DeepSeek fetch 搞定，但如果用户要读的是本地 PDF、DOCX、EPUB、图片甚至音频呢？我不希望把本地私密文档传给第三方接口，必须在本地完成转换。

我选择了 [anymd](https://github.com/SylphxAI/anymd)。它能把各种格式本地转成 Markdown。它本身支持直接传入 URL 解析，我起初想省去下载文件的步骤：

```text
anymd: https://arxiv.org/pdf/1706.03762: URL host 'arxiv.org' resolves to a non-public address (SSRF protection).
```

这又绕回了之前的 TUN 代理问题：`arxiv.org` 被解析成了 `198.18.7.138`。但 anymd 是编译好的 Rust 二进制程序，在二进制字符串里翻了个遍，也没有关闭 SSRF 检查的开关。

解决办法：**永远先下载到本地临时文件，再把本地文件路径喂给 anymd**。这样既绕过了它的 SSRF 检查，也能顺手做文件大小限制（限制单文件 30MB）与自动清理。

这里还踩过一个小坑：最开始我是用 `arrayBuffer()` 把 30MB 完整读进内存再写入磁盘，3 个并发抓取峰值内存就是 90MB；后来改成 Node.js stream pipeline 流式落盘，内存峰值直接降到了几十 KB。

## 中文扫描件乱码：12 行 shell shim 救场

解决了文件读取，又发现中文 OCR 有问题。anymd 底层调用 tesseract 的命令是 `tesseract <image> stdout`——完全没有指定 `-l` 参数，默认只认英文字符。中文扫描件跑出来的结果是一堆不知所云的拉丁乱码。

我不想 fork anymd 重新编译整个 Rust 工程，于是写了个 12 行的 shell shim，把它排在系统的 PATH 前面：

```bash
#!/bin/bash
REAL=/opt/homebrew/bin/tesseract
for arg in "$@"; do
  case "$arg" in
    -l|--oem|--psm) exec "$REAL" "$@" ;;
  esac
done
exec "$REAL" -l "${ANYMD_TESS_LANGS:-chi_sim+eng}" "$@"
```

逻辑很简单：如果调用方显式指定了语言参数，就原样转发；如果没传，自动注入 `-l chi_sim+eng`。这个脚本现在作为 `bin/tesseract` 随扩展一起打包，装好 tesseract 语言包后开箱即用。

## 实测对比：本地结构化解析到底值不值？

为了确认引入 anymd 不是盲目增加复杂度，我拿 15 页的 Attention 论文和 75 页的 GPT-3 论文做了对照实验：

| 工具 | 提取字数 | 标题数 | 表格行数 | 行尾连字符错误 | 乱码字符 | 解析耗时 |
|---|---|---|---|---|---|---|
| anymd | 41,026 | **26** | **146** | 0 | 0 | 0.22s |
| pdftotext -layout | 59,444 | 0 | 0 | 16 | 15 | 0.09s |
| pdftotext (raw) | 39,919 | 0 | 0 | 0 | 15 | 0.11s |
| mutool -F txt | 40,067 | 0 | 0 | 16 | 16 | 0.14s |

实验结果展现的不是简单的优劣，而是**它们失败的模式完全不同**：

- 传统工具输出的是纯粹的"文本流"。遇到双栏论文时，左右两栏的文字经常会穿插在一起（例如一句话没讲完紧接着另一栏的内容），短行比例超过 60%，模型读起来非常吃力；
- anymd 输出的是清晰的"文档结构"：标题层级完整（`## 3 Model Architecture` → `### 3.1 Encoder and Decoder Stacks`），表格能还原成 Markdown 管道表，图片和图注被转换为占位符并标明页码。
- 代价是耗时慢了 2 倍左右（0.22 秒 vs 0.09 秒），偶发有表格列轻微错位。

但有一点大家都没解决：**数学公式**。无论是哪种工具，提取出的公式都像 `Attention(Q, K, V ) = softmax( √ )V (1) d_k`，根号里的内容完全丢失了排版。这是 PDF 格式本身字形定位的局限，不是文本提取工具能够完全弥补的。

## 打包时遇到的 `import.meta.url` 陷阱

在本地开发时，扩展直接软链接到 `~/.pi/agent/extensions/`，用 `import.meta.url` 定位同目录下的 `bin/tesseract` 毫无问题。

但打包成 npm 包、通过 `pi -e` 动态加载后，扩展启动直接报错：

```text
[pi-deepread] shim:  exists: false
```

排查后发现：Pi 内部使用 jiti 加载扩展，模块被转换成了 CommonJS 执行，此时 `import.meta` 是个空对象。

最终做了降级处理：优先尝试 `import.meta.url`（ESM 场景）；若拿不到，退回使用 `eval("typeof __dirname === 'string' ? __dirname : ''")`（CJS 场景）；若两者都失败，则静默放弃注入 shim。

**降级应当是静默的**。不能因为一个可选的中文 OCR shim 找不到，就导致整个核心搜索扩展崩溃。

## 主动舍弃的功能

有些功能在初期考虑过，但权衡后主动放弃了：

- **抓取 YouTube 字幕**：DeepSeek 搜索出的 YouTube 链接往往指向 `music.youtube.com`，需要针对不同链接类型写一套特殊的解析逻辑，性价比太低；
- **图片搜索**：日常使用场景中，写代码和查资料对以图搜图没有刚需；
- **缓存文件 gzip 压缩**：压缩虽然能省约 70% 的磁盘空间，但每次读写都需要做解压，不仅增加了延迟，还引入了额外的状态逻辑。配合 7 天 / 200 个文件 / 64MB 的自动淘汰策略，纯文本存储已经足够轻巧；
- **会话内 URL 内存缓存**：看似能避免重复抓取同一个链接，但容易把陈旧内容返回给模型。在实际使用中，同一个会话里重复读取同一网页的概率极低，不值得增加复杂度；
- **并发调高到 5 以上**：速度虽然能稍微提升一点，但 429 报错的概率会明显增加。3 是实测出来的最佳平衡点。

## 如果你也想写类似的扩展

回顾整个过程，几条最管用的开发心得：

1. **先用 curl 摸底，再动手写代码**。直接看 API 文档容易漏掉很多隐藏逻辑，把请求体、返回格式、边界条件抓一遍，很多弯路一开始就能避开；
2. **错误信息一定要把上下文带上**。query 超长时把拼好的字符串打出来，抓取失败时标明具体的 URL 和原因，排查问题的效率会高很多；
3. **核心路径要清晰报错，可选功能要静默降级**。DeepSeek 挂了必须明确提示切换到 Exa，但 OCR shim 找不到只需在状态里记录一条提示；
4. **别去修改依赖包编译后的 dist 文件**；
5. **把实测数据随手记下来**。这不仅能避免凭感觉做判断，三天后也能有一把客观的标准来衡量系统表现。
