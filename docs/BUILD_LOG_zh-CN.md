# pi-deepread 开发手记：从一条推文到单文件扩展

[English](BUILD_LOG.md) | 简体中文

> 这不是一份循规蹈矩的使用教程，而是一篇坦诚记述真实想法、踩坑经历与架构取舍的个人手记。代码大多在 AI 辅助下编写完成，而所有的需求设计、故障排查、权衡折中与实操验证，都来自我自己的真实调试过程。文内记录的全部测试数据，均在我的电脑上实测得出。

## 灵感乍现：搜索本来就能直接带回全文，何必多折腾一次？

一切始于我偶然刷到的 [@Arcadia_Bao 的推文](https://x.com/Arcadia_Bao/article/2111711040757006401)。他在文中对 DeepSeek 的 Search 与 Fetch 接口做了全面评测，其中有一句话瞬间击中了我：

> 默认务必开启 `need_content: true`。完全不需要额外加钱，每次调用依然只要 ¥0.005。

这意味着，一次普通的搜索请求带回来的不仅是标题和短摘要，而是每一条搜索命中背后**提取好的完整网页正文**。在实际测试中，每个结果往往包含 3,700 到 12,600 个字符；遇到 arXiv 论文页面，甚至能一次性带回近 30,000 字符的正文。

当时我日常使用的工具是 `pi-web-access`，它的运作流程是经典的“先搜摘要，再抓正文”：一次搜索返回几条 800 字符左右的碎片摘要，模型看完觉得信息不够，只能再触发一次工具调用去拉取网页正文。整整两轮网络往返，响应耗时直接翻倍。如果第一次搜索就能直接把完整正文双手奉上，绝大部分“搜索再抓取”的冗余交互根本就没有存在的必要。

现有的扩展都没有启用这个参数。既然如此，我决定自己写一个。

## 第一天：一头撞上 TUN 代理的 Fake-IP 墙

我快速搭了一个原型脚本，兴致勃勃地跑了抓取测试，结果终端迎面拍来一行鲜红的报错：

```text
Error: Blocked internal address for x.com: 198.18.0.14.
This address is in 198.18.0.0/15, commonly used by TUN/fake-IP proxies.
```

我的第一反应是代码里的 SSRF 防御校验写崩了。好端端的 `x.com`，怎么就成了局域网私有 IP？

回过神来才意识到：我的电脑平时挂着 TUN 模式的代理客户端（Clash/Surge）。在透明的 Fake-IP 模式下，所有的 DNS 查询都会被系统拦截并分发一个保留网段 `198.18.0.0/15` 下的虚拟 IP；真实的流量调度是在底层由代理软件根据域名来完成的。与此同时，我的扩展为了防止恶意网页诱骗模型去探测云厂商内网元数据（比如 `169.254.169.254`）或局域网服务，把所有的保留网段全部封死了。结果 `198.18.0.0/15` 恰好被一枪击中。

解决起来倒也干脆，在配置里留一个显式白名单：

```json
{
  "ssrf": {
    "allowRanges": ["198.18.0.0/15"]
  }
}
```

这里的安全权衡必须直说：加上这行配置，等于告诉工具“放行该网段，全权交由代理处理”。在 TUN 环境下这很安全，可一旦电脑断开了代理，这个例外就会变成一个潜在的安全缺口。因此它必须由用户显式开启，绝不能作为默认配置存在。

## curl 摸底：那些官方文档里从没写过的潜规则

理顺了代理配置，我顺手试着抓取当初那条推文。结果 `x.com` 干净利落地甩回了一个 `HTTP 403`。我又尝试走公共代理 `r.jina.ai`，迎面又撞上了 Jina 的风控黑名单：

```json
{"code":403,"name":"AbuseAlleviationError","message":"Anonymous access to domain x.com blocked until Sun Oct 18 2026..."}
```

折腾了一圈，最后我还是私信朋友，让他帮我把推文内容手动复制粘贴了过来。

这个小插曲结结实实地给我提了个醒：网页抓取失败通常发生在三个不同层级：
1. **网络层**（请求超时、429 频控）；
2. **目标站点层**（403 封锁、付费墙、强制登录）；
3. **代理服务层**（像 Jina 这类公共代理自带的配额限制和域名黑名单）。

第三层尤其容易让人心烦意乱，因为它常常诱导你反复怀疑自己的本地代码，而你的代码其实完全没有问题。

为了避免继续在隐形暗坑里浪费时间，我决定先停下写扩展代码的手，打开终端用纯粹的 `curl` 逐个摸清 DeepSeek 接口的真实脾气。事实证明，这是整个开发过程中最明智的一个决定：

### 1. `need_content` 默认是不开启的

直接调用原生的搜索接口，不加 `need_content` 参数：

```text
content_len = 0
summary_len = 431
```

你只能拿到一段 431 字符的短摘要，页面正文直接为空。只有显式传上 `need_content: true`：

```text
content_len = 3739 / 12614
authority = 3, rerank_score ≈ 2.19
```

每条搜索结果瞬间带回了数千字提取好的网页正文。如果我当初没有先用 curl 摸底，搜索表面上能返回标题和链接，看似一切正常，但背地里模型拿到的永远只有干瘪的摘要，而我可能会花上好几天的时间去苦思冥想为什么 DeepSeek 抽不出全文。

此外，DeepSeek 在返回中自带了两个实用字段：`authority`（权威度 0–4，≥3 表示高权威）和 `rerank_score`（重排得分 0–3，≥1.5 表示高匹配度）。这些都是模型官方计算好的现成指标，拿来就能直接用，完全不需要我们在本地再自造一套玄学排序算法。

### 2. 128 字符硬限制与算子反噬

最开始我自以为聪明地把 `domainFilter` 和 `recencyFilter` 直接编译成 `site:` 和 `after:` 算子拼进了查询关键词里。心想这样能省去维护额外参数的麻烦，结果一条稍微有点长的搜索词当场爆掉：

```text
HTTP 400 {"error":{"message":"'query' must be at most 128 characters (request_id: ...)"}}
```

原来 DeepSeek 校验的是*最终拼接完成后的查询字符串总长*。这些过滤算子直接吃掉了宝贵的 128 字符额度。

针对这个问题的解法是：拼接完成后在本地预先测量总长度。如果超出了 128 字符且用户配置了 Exa Key，就把整条查询转交给没有字数限制的 Exa 处理；如果用户没配 Exa Key，则立即报错，但要在报错信息中把拼好的完整查询字符串完完整整地打印出来，让用户一眼就能看出到底是哪里撑爆了字数。

在错误信息里提供完整的上下文，帮我省下了无数抓瞎调试的时间。

### 3. 并发测试：10 线程必撞 429，3 线程稳如泰山

压测数据非常残酷：一旦并发数开到 10，大约 30% 的请求会在 600ms 内被服务商以 `HTTP 429` 拒之门外。

虽说 429 不算计费调用，但指数退避重试带来的延迟会让使用体验大打折扣。

我写的第一个版本采用了最保守的纯串行模式，每次请求强制休眠 900ms。稳定确实稳定，但抓取 4 个 URL 整整耗费了将近 6 秒——绝大部分时间都浪费在干等定时器上了。

经过反复调优，最终找到了最佳平衡点：**3 个并发槽位，配合 gap/3（300ms）的错峰启动延迟**：
- 任意时刻正在飞行的网络请求绝不超过 3 个（牢牢守在限流阈值之下）；
- 每个新请求之间错开 300ms 依次发出。

抓取 4 个 URL 的总耗时直接从 5.71 秒腰斩至 **2.85 秒**，且没有触发任何 429 报错。

## 偷懒的诱惑：为什么我不去打别人的压缩包补丁？

在逆向分析 `pi-web-access` 的代码时，我找到了它截断 DeepSeek 搜索正文的那行罪魁祸首：

```javascript
snippet: (text4(entry.summary) || text4(entry.snippet)).slice(0, MAX_SNIPPET_CHARS4)
// MAX_SNIPPET_CHARS4 = 800
```

而且在它发出的请求体里，连 `need_content` 的影子都没有（在 `dist/index.js` 搜 `need_content` 结果是 0）。上游的 582 号 Issue 已经挂了很久，无人问津。

我当时真动过走捷径的念头：直接打开本地安装的打包文件，把 800 改成 8000，完事收工。我甚至顺手跑了 `node --check`，代码还真能跑通！

但理智很快把我拉了回来：

1. 扩展只要一升级，我的本地补丁立刻烟消云散；
2. 在一份超过 1MB 且变量名全被混淆的单文件 bundle 里改逻辑，一旦出问题排查起来就是纯粹的折磨；
3. 最关键的是，我的初衷根本不是简单地把摘要上限从 800 放宽到 8,000 字符。我真正想要的是基于 `responseId` 将正文缓存到磁盘、优雅的分页浏览机制，以及能让模型直接精准跳转到关键段落的 `findText` 功能，避免一抓全文就把上下文窗口挤爆。

因此我下定决心从零写起：1,300 行 TypeScript，单文件架构，零运行时依赖。现在回过头来看，这绝对是整个项目里做出的最正确决定。

## 本地文档解析：anymd 与第二处 SSRF 陷阱

网页内容可以通过 DeepSeek fetch 搞定，但如果用户想让 Pi 读取本地的 PDF、Word 文档、Excel 表格、EPUB、图片甚至录音文件呢？在这件事上我态度很坚决：敏感的本地文档绝对不能上传到外部 API，一切转换必须 100% 在用户的本地电脑上完成。

我挑选了 [anymd](https://github.com/SylphxAI/anymd)。它能把形形色色的格式转换成排版工整的 Markdown。它甚至原生支持直接传 URL，所以我一开始尝试把网页 URL 直接塞给它，想着省去本地先下载文件的步骤：

```text
anymd: https://arxiv.org/pdf/1706.03762: URL host 'arxiv.org' resolves to a non-public address (SSRF protection).
```

历史总是惊人地相似，TUN 代理的坑又杀回来了！`arxiv.org` 被 Fake-IP 解析成了 `198.18.7.138`。但与我自己的代码不同，`anymd` 是预先编译好的 Rust 二进制程序。我在它的二进制字符串里翻了个底朝天，也没找到任何可以关闭内部 SSRF 检查的配置项或环境变量。

最终的解法非常务实：**永远先把网页流式下载到本地临时文件，再把本地文件路径转交给 anymd**。这样既巧妙避开了 `anymd` 自身的 SSRF 拦截，又能顺带做统一的文件大小限制（硬性卡死 30MB 上限），并确保退出时临时文件会被自动清理。

这里还藏着一个容易忽视的内存坑：我的最初版本直接用 `arrayBuffer()` 把 30MB 文件整坨读进内存再写入磁盘。当 3 个并发下载同时跑起来时，Node.js 进程的内存瞬间飙高了 90MB。后来改用 Node.js 的 stream pipeline 管道流式落盘，峰值内存占用直接被压平到了区区几 KB。

## 中文扫描版 PDF：12 行 Shell 脚本救场

本地文件解析跑顺之后，中文 OCR 又翻了车。`anymd` 底层调用 Tesseract 时的命令是 `tesseract <image> stdout`，完全没有带 `-l` 语言参数，Tesseract 默认只走英文模式。导致扫描版中文文档解析出来的全是一串串不知所云的拉丁字母乱码。

为了给 CLI 补上几个参数就去 Fork `anymd` 并在本地配 Rust 环境重新编译，未免有些小题大做。我换了个思路：顺手写了一个 12 行的 Shell 包装脚本，把它扔在 `PATH` 环境变量中系统二进制的前面：

```bash
#!/bin/bash
REAL=/opt/homebrew/bin/tesseract
for arg in "$@"; do
  case "$arg" in
    -l|--oem|--psm) exec "$REAL" "$@" ;;
  esac
done
exec "$REAL" -l "${ANYMD_TESS_LANGS:-chi_sim+eng}" "$@"
```

核心逻辑很纯粹：如果调用方显式传了语言或模式相关的参数，脚本就原封不动地直接透传调用；如果什么都没传，就自动注入 `-l chi_sim+eng`。这个小脚本现在就放在仓库的 `bin/tesseract` 里——用户只需安装好 `tesseract-lang`，中文 OCR 就能开箱即用，不需要折腾任何其他设置。

## 性能实测：结构化 Markdown 到底值不值？

为了验证引入 `anymd` 究竟是真有必要还是在徒增复杂度，我专门找了两篇重磅论文做了实测对照：15 页的 *Attention Is All You Need* 和 75 页的 *GPT-3* 论文：

| 解析工具 | 提取字符数 | 识别标题数 | 提取表格行数 | 连字符断行错误 | 乱码字符数 | 耗时 |
|---|---|---|---|---|---|---|
| anymd | 41,026 | **26** | **146** | 0 | 0 | 0.22s |
| pdftotext -layout | 59,444 | 0 | 0 | 16 | 15 | 0.09s |
| pdftotext (raw) | 39,919 | 0 | 0 | 0 | 15 | 0.11s |
| mutool -F txt | 40,067 | 0 | 0 | 16 | 16 | 0.14s |

测试数据揭示了一个至关重要的结论：**这几款工具的失效模式是截然不同的**。

- 传统的命令行文本工具吐出来的是毫无结构的“字符流”。遇到学术论文的双栏排版时，左右两栏的句子常常交错混杂在一起，超过 60% 的行直接沦为残缺断句。大语言模型拿到这种文本，得先耗费大半的推理能力去人肉拼凑语序。
- `anymd` 能够精准还原文章的语义层级：标题结构清晰严整（`## 3 Model Architecture` → `### 3.1 Encoder and Decoder Stacks`），表格被整齐规整为 Markdown 管道表格，图片也能附带图注与原文档页码转为占位说明。
- 为此付出的代价是耗时多出一倍（0.22 秒对 0.09 秒），且面对极复杂的表格时偶有对齐瑕疵。但对于需要深度阅读技术文档的 AI Agent 而言，这笔代价付得非常值。

不过，这两类工具都没能攻克数学公式：像 `Attention(Q, K, V ) = softmax( √ )V (1) d_k` 这种公式，根号内的表达式排版依然会丢失。这是 PDF 格式字形绝对定位机制造成的物理硬伤，并不是单纯依靠文本提取工具就能凭空变出来的。

## 打包陷阱与 `import.meta.url` 的意外

本地开发阶段，我在 `~/.pi/agent/extensions/` 下建了软链接，代码里用 `import.meta.url` 来定位旁边的 `bin/tesseract` 补丁脚本，一直运行得顺风顺水。

直到我将它打包并推到 npm，用 `pi -e` 启动测试时，终端突然当头泼来一盆冷水：

```text
[pi-deepread] shim:  exists: false
```

排查了一圈才恍然大悟：Pi 底层是通过 `jiti` 来动态加载扩展的，在运行时会将模块即时转译为 CommonJS 执行。在这种环境下，`import.meta` 直接变成了一个空对象。

最终我采用了多层回退策略：优先读取 `import.meta.url`（适配原生 ESM 环境）；若拿不到，退回使用 `eval("typeof __dirname === 'string' ? __dirname : ''")`（适配 CJS 环境）；若依然取不到，则静默放弃注入补丁。

**功能的平滑降级必须做到静默无感。** 绝不能因为一个可选的中文 OCR 补丁找不到，就把整个核心的搜索功能搞崩溃。

## 那些被我主动砍掉的功能

在项目早期，有几个功能看起来颇具诱惑力，但在仔细权衡维护成本后，我都毫不犹豫地砍掉了：

- **抓取 YouTube 视频字幕**：DeepSeek 搜索出来的 YouTube 链接常常被定向到 `music.youtube.com`，需要写很多冗杂的 URL 纠错规则，投入产出比极低。
- **以图搜图**：在专注于代码编写和技术文档查阅的 Agent 场景中，这类需求几乎不存在。
- **缓存文件 gzip 压缩**：压缩确实能省下约 70% 的磁盘空间，但每次读写都要额外解压，平白增加了系统延迟。配合简单明了的淘汰机制（7 天保留 / 200 个文件上限 / 64MB 容量封顶），纯文本存储的维护成本反而低得多。

有意思的是，有两个最初被我狠心砍掉的特性，在后来我真正开始做全量基准测试后又被重新请了回来——也就是下面要聊的第二轮演进：会话内 URL 缓存与按域名独立调度并发。

## 第二轮：当我真正开始用基准测试衡量一切

发布一个月后，在没有做任何主动推广的情况下，这个扩展在 npm 上悄然积累了大约 270 次月下载。看到真有用户在日常工作中依赖它，我意识到该踩刹车了：停止盲目堆砌新功能，老老实实把已有的机制测深测透。我搭建了 `bench/` 测试套件——它会通过 Pi 真实的模块加载器来载入扩展，因此下方表格里的每一个数据，都是真实发起的 API 调用实测，绝无半点凭空估算。

由于测试脚本需要完全模拟 Pi 的加载流程，运行时需要将 Pi 自身的 `node_modules` 软链接过来：`ln -s ~/.pi/agent/install/releases/<版本号>/node_modules node_modules`，随后执行 `node bench/prompt-surface.ts` 或 `node bench/scenarios.ts [p0|p1|p2]`。（这个软链接仅在本地有效，不会提交进 git 仓库。）

| 测试项目 | 优化前 | 优化后 | 为什么会发生变化 |
| --- | --- | --- | --- |
| 常驻 Prompt 占用 | 5,896 字符 / 1,638 tokens | 3,494 字符 / 971 tokens | 将指导模型如何使用的说明移入工具返回值，不再死占系统提示词空间 |
| 付费墙页面返回正文的比例 | 6 个站点命中 0 个 | 6 个站点命中 **5 个** | 阅读代理与 Wayback Machine 网页快照并行竞速提取 |
| 仅限浏览器渲染的纯 JS 页面 | 12 秒超时后报错中断 | 2.8 秒，提取到 53 KB 正文 | 正文提取器没问题，是原先死磕直连的抓取策略错了 |
| arXiv 论文页面访问 | 6,436 毫秒 | 804 毫秒 | 只要存在 HTML 版本（`/html/`），优先抓取 HTML 而非死磕 PDF |
| 无 HTML 版本的早期 arXiv 论文 | 5,955 毫秒 | 273 毫秒 | 识别到论文早于 arXiv HTML 项目上线时间，立即放弃无意义的重试 |
| 6 个请求并发抓取 | 9,314 毫秒 | 2,727 毫秒 | 改为按目标域名调度并发，告别全局固定上限 3 的排队拥堵 |
| 二次抓取完全相同的 URL | 7,042 毫秒 | 1 毫秒 | 会话内热缓存毫秒级返回 |
| 给 Agent 喂本地 PDF 文件 | 报错“Blocked internal address” | 143 毫秒返回提取正文 | 修正逻辑：本地文件路径是本地资源，绝不能当成网络 URL 处理 |
| 维基百科 Markdown 提取 | 105 KB 伴随 4 行冗余元数据 | 100 KB 仅剩 1 行元数据 | 将去噪范围精准限定在 `<article>` 与 `<main>` 语义标签内部 |
| 163 字符超长过滤查询 | 抛出硬性错误中断任务 | 617 毫秒返回有效结果 | 智能修剪超长查询，绝不粗暴抛错 |
| 5 条结果 × 单条 6,000 字符 | 只有 3 条能带回正文 | 5 条完整带回正文 | 在字符预算分配中为每一条搜索命中预留了最低保障额度 |
| 6 条结果中的重复站点 | 1–3 个域名重复 | 0–1 个，总结果数保持不变 | 预先多取 2 条结果，再剔除重复链接、同域名第 3 条命中及通稿转载 |
| 伪装成正文的 JS 空壳页面 | 把 123 字符的微博导航当正文返回 | 准确识别为拦截墙 | “无长段落正文 + 导航结构超标”比机械的关键词黑名单靠谱得多 |

这一轮重构带来了三条在最初写手记时未能领悟的心得：

**系统提示词是所有人都在默默承担、却从没人认真测量的隐形重税。** 1,638 tokens 的常驻 Prompt 占用，意味着用户在会话里的每一轮对话、哪怕只是随口问一句“如何退出 vim”，这笔 token 成本都要原封不动地被计费一次。而这其中大部分内容，是在指导模型“拿到搜索结果后该怎么做”。把这部分指引顺水推舟放到工具的返回内容里，常驻的 Prompt 占用立刻被压缩到了 1,000 tokens 以内（约 3,500 字符）。核心原则：工具的描述只应讲清楚“这个工具是什么”，而不是在上门推销时长篇大论地教模型怎么做人。

**“加一层后备通道”和“再死磕重试一次”是完全不同的系统架构。** 在处理付费墙的第一版逻辑里，如果常规请求失败，代码就依次尝试备选方案——这相当于把每一次失败的等待时间直接翻倍。后来改为将阅读代理与 Wayback Machine 快照并发同时发出、竞速抢答，原本令人绝望的 12 秒超时等待，在完全相同的底层逻辑下，直接变成了 2.8 秒的即时响应。

**那些曾被你自以为是推翻的想法，值得堂堂正正写进标题，而不是藏在角落当个注脚。** 在 v0.1 版本里，我以“同一个会话极少重复抓取相同链接”为由砍掉了内存缓存。现实狠狠打了我的脸：当 Agent 经历了上下文压缩重整、反复重读接口文档、或是多次搜索命中了同一网站的不同锚点时，重复抓取极为频繁。还有那个全局并发限制为 3 的决定，其实非常荒谬：它强行把发往不同域名的请求排成了一条长队，而那些站点之间根本不存在相互限流的可能。现在这两项功能全部重构归位，带来的性能提升整整跨越了 1 到 2 个数量级。

## 掏心窝的几条实战建议

如果你也在为编程 Agent 编写工具类的扩展插件，以下几点是我踩坑换来的心法：

1. **写代码之前，先用 curl 抓包探路。** 永远别迷信那些可能早就过时的文档。亲手把原始的请求体、报错结构和默认参数跑一遍，能替你避开绝大部分暗坑；
2. **在报错信息里尽可能带全上下文。** 查询太长了，就把拼装后的完整查询打印出来；抓取失败了，就明确标注请求的 URL 和当时走到了哪一层备选链路。排查问题时这会救你一命；
3. **核心功能故障要大声报错，可选增强特性要静默降级。** DeepSeek API 欠费了必须明确告知用户已回退到 Exa；如果只是缺失了一个可选的 OCR 脚本，安安静静在 `/web-status` 里留一条状态记录就好；
4. **永远别动依赖包打包后的 dist 代码；**
5. **边写代码边记录真实数据。** 这不仅能让你在写 README 时心里有底，更重要的是在一周之后，你能有一把客观的尺子，清清楚楚地检验最新的改动到底是在优化还是在劣化。
